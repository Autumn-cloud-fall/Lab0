    答:Gitflow 使用规范（基于图片及通用知识）
    概括内容：
    该网页主要介绍了 Gitflow 这一经典的 Git 分支管理模型。
    背景与目的：文章指出 Git 是基于分支的版本管理系统，为了在多人协作中避免代码冲突、保证代码版本稳定，衍生出了多种分支管理策略。Gitflow 是其中极具代表性的一种，许多公司的规范都受其影响。
    核心分支：Gitflow 定义了两种主要分支：
     master （主分支）：用于存放随时可发布的稳定代码，每次发布都会在此打标签。
     develop （开发分支）：用于日常开发集成，是下一次发布的集成测试分支。
    辅助分支：为了支持并行开发，还引入了三种辅助分支：
     feature （功能分支）：从  develop  切出，开发新功能，完成后合并回  develop 。
     release （发布分支）：从  develop  切出，用于发布前的最后准备（如版本号修改、bug 修复），完成后合并到  master  和  develop 。
     hotfix （热修复分支）：从  master  切出，用于紧急修复生产环境的 bug，完成后合并到  master  和  develop 。
    总结：Gitflow 通过严格的分支职责划分，使得团队协作更加有序，特别适合有明确发布周期的项目。
    通过学习上述内容，我对“为什么要学习 Git”有了以下深刻理解：
    1.它是现代软件工程的“基础设施”：
    正如文中提到“如果你严肃对待编程，就必定会使用版本管理工具”。无论是个人项目还是企业级开发，代码的迭代是必然的。Git 作为事实上的行业标准，是团队协作的通用语言。不学 Git，就无法真正参与到正规的软件开发流程中。
    2.它是代码安全的“保险箱”：
    Git 能够完整记录代码的每一次变更。在开发过程中，我们经常会尝试一些有风险的重构或新功能。有了 Git，我们可以大胆尝试，因为一旦出现问题，可以瞬间回滚到之前的稳定状态。这种“后悔药”机制极大地降低了开发风险。
    3.它是多人协作的“协调员”：
    在团队中，多人同时修改代码必然会产生冲突。Git 提供了强大的合并（Merge）和变基（Rebase）机制，配合像 Gitflow 这样的分支策略，能够清晰地管理谁在什么时间修改了什么，如何将这些修改安全地集成到主线上。它让协作从“互相覆盖”变成了“有序集成”。
    4.它提升了开发效率与灵活性：
    Git 的分布式特性让开发者可以在本地完成大部分版本操作，无需时刻依赖网络。同时，轻量级的分支让“并行开发”变得极其容易。我们可以为每个新功能创建一个分支，互不干扰，开发完成后再统一合并。这种灵活性是高效迭代的关键。
    综上所述，学习 Git 不仅仅是在学一组命令行工具，更是在学习一种规范的代码管理思维和高效的协作方法论。它是程序员从“单打独斗”走向“专业工程化”的必经门槛。

    - 在两个分支上的提交必须要满足：在 `main` 分支合并时会出现冲突。请你解决这个冲突，并在实验报告里截图表明你遇到并解决了冲突。
    冲突产生原理：
    Git 合并冲突通常发生在两个分支对同一文件的同一部分进行了不同的修改。在上述步骤中， main  分支和  feature  分支都在  main.c  的 。由于这两行添加的位置完全相同，Git 无法自动判断应该保留哪一行，因此会产生冲突。
    ![合并冲突界面](./confict.png)
    - 请阅读 `git merge` 部分，思考如何修改 `main.c` 会出现冲突。
    答：如何修改会出现冲突：
    1.同一行修改： 如果两个分支都修改了同一行的内容（例如将  printf("Hello, Git!\n");  分别改成不同的字符串），合并时会冲突。
    2.相邻行添加： 如果两个分支在完全相同的位置（例如都在第 5 行后）添加了不同的内容，也会冲突。
    3.删除与修改冲突： 如果一个分支删除了某一行，另一个分支修改了同一行，合并时也会冲突。
    4.不会冲突的情况：
    两个分支修改了文件的不同部分（例如  main  修改第 3 行， feature  修改第 10 行），Git 可以自动合并。
    一个分支添加行，另一个分支在远离该位置的地方修改，通常不会冲突。
    - 如果你两次提交之后合并没有出现冲突，不必担心，你可以不用撤回之前的提交，而是继续尝试提交修改并 merge，直到出现冲突并解决。
